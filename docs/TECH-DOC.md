## 第 1 章 意图控制策略（如何设计与驾驭 AI）

### 1.1 开发期的意图控制：让 AI 生成「可控」的代码

本项目全程采用 AI 协同开发（Vibe Coding），意图控制不是「一句话生成整个项目」，而是**分层递进的表达策略**：

| 层次 | 手段 | 实例 |
| --- | --- | --- |
| 架构层 | 先与 AI 对齐技术选型与目录骨架，一次定型 | Spring Boot 3 + Spring AI + 双模式向量存储的分层方案 |
| 模块层 | 每个功能用「目标 + 约束 + 验收标准」三段式 Prompt | 「实现 SSE 流式问答，事件协议为 sources/message/done，错误走 error 事件且连接不断开」 |
| 修复层 | 贴**日志原文**而非现象描述，让 AI 基于证据推理 | 「`WARN Retry error: HTTP 404` + reindex 成功但向量数为 0」 |
| 边界层 | 明确「不许动什么」防止 AI 过度重构 | 「把项目搞成向量化，不许改提示词、RAG 策略等别的」 |

三个核心迭代中意图控制的完整对话链见 **[docs/prompt-history/](prompt-history/README.md)**。

### 1.2 运行期的意图控制：让大模型生成「可信」的回答

系统内的提示词工程针对**防幻觉**这一核心意图设计，`qa-system-prompt.st` 包含 6 条硬性约束：

1. 仅依据提供的制度原文回答，**禁止使用训练语料里的通用知识**
2. 制度中无依据时，必须明确回答「现有制度中未涉及该问题」
3. 每个论断标注来源页码 `[第X页]`，**页码只能来自检索结果的元数据，禁止估算**
4. 多个来源冲突时指出冲突而非自行裁决
5. 使用规范、中性的公文语气
6. 列举类问题优先用列表呈现，与原文条目一一对应

配合代码层的三道防线（见 2.3），形成「提示词约束 → 检索闸门 → 引用可核对」的完整抗幻觉链路。

### 1.3 上下文管理

- **检索上下文**：Top-3 文本块（各 ≤200 字）+ 元数据（文档标题、页码、相似度）注入提示词，总长度可控且不淹没关键信息
- **对话上下文**：sessionId 隔离会话，历史记录落库 `t_chat_record`，支持追问场景
- **失败上下文**：生成失败时不中断 SSE 连接，降级推送制度原文摘录——用户始终拿到「有用」的输出

## 第 2 章 架构设计

### 2.1 总体架构与技术选型理由

```
Vue3 (SSE 消费 / Markdown 渲染)
   │  fetch + ReadableStream
Spring Boot 3
   ├─ PdfIngestService   解析/切分/向量化（写入路径）
   ├─ RagQaService       检索/闸门/生成/来源引用（查询路径）
   ├─ DeepSeekClient     自研客户端（流式/思维链开关）
   └─ VectorStore 接口   ← 业务代码只依赖此抽象
        ├─ JdbcCosineVectorStore (local: 普通表 + Java 余弦)
        └─ PgVectorStore         (railway: pgvector + HNSW)
PostgreSQL (Flyway V1~V4 迁移)
```

关键选型决策：

- **读写分离的两个独立服务**：写入路径（上传→入库）与查询路径（提问→检索）各自独立演进，互不影响
- **向量存储抽象成接口 + 双实现**：目标机器装不上 pgvector（Windows 无官方扩展）是真实约束，双模式让同一份代码在「任何 PostgreSQL」与「pgvector」之间零改动切换
- **生成与向量化供应商分离**：DeepSeek 不提供 Embedding 接口（官方文档确认），因此 Embedding 走 OpenAI 协议兼容层（硅基流动 bge-m3，免费），任何兼容服务可替换——架构上不存在供应商锁定

### 2.2 AI 生成代码的架构约束

AI 生成的代码容易发散，本项目用三个手段把它约束住：

1. **分层铁律**：Controller 只做协议转换；业务在 Service；AI 调用收口在 `ai/` 包（`DeepSeekClient`、`EmbeddingService`、`VectorStore`）；持久化只在 Repository。任何一次生成任务只允许触碰对应层
2. **配置外置**：模型名、阈值、Top-K 全部走 `application.yml` + 环境变量（`campus.qa.*`、`campus.deepseek.*`），代码中不允许出现魔法数字
3. **契约先行**：SSE 事件协议（`sources → message* → done`，错误走 `error`）与统一响应体 `{code, message, data}` 先定义后实现，前后端可并行开发

### 2.3 可靠性设计（亮点）

| 机制 | 解决的问题 | 位置 |
| --- | --- | --- |
| Embedding 熔断器 | Key 失效时每次提问都等 19~42s 网络超时 | `JdbcCosineVectorStore`（失败即熔断 10 分钟，自动恢复；启动时识别占位 Key） |
| 关键词检索兜底 | Embedding 不可用时检索完全失效 | 中文 2-gram 匹配，与语义路合并排序 |
| 相关性闸门 | 相似度全低仍硬答 → 幻觉 | `RagQaService`：Top-K 全低于阈值则不调大模型 |
| 生成降级 | DeepSeek 失败时用户拿到空白 | SSE 不中断，推送制度原文摘录 |
| 参数校验走事件通道 | `@Valid` JSON 错误体与 `text/event-stream` 冲突（406） | 校验下沉 Service，错误经 `error` 事件下发 |

### 2.4 检索透明化（亮点）

传统 RAG 对用户是黑盒：为什么这么答？依据可信吗？本系统把检索打分过程完整暴露给用户——每轮回答附带一个 `RetrievalTrace` 快照，前端以「为什么这样答」面板呈现：

- **全量候选打分**：`JdbcCosineVectorStore#similaritySearch` 不再在存储层截断，返回全部候选及其余弦分数；阈值过滤与 Top-K 截断职责上移到 `RagQaService#prepare`，职责更清晰且可观测。
- **Trace 结构**：记录模式（semantic / keyword / keyword-fallback）、阈值、TopK、检索耗时、熔断状态、闸门结论（`PASS` / `REJECT_ALL_BELOW_THRESHOLD`）与人话解释，以及最多 20 条候选（标题 + 页码 + 分数 + 是否命中 + 原文片段）。
- **传输**：SSE 协议升级为 `trace → sources → message* → done`，trace 事件先于正文到达；同步接口 `/api/qa/ask` 响应体同样携带 `trace`。
- **前端呈现**：分数条主色渐变 + 阈值竖刻度线，命中/未命中徽标，拒答时用「宁可不答也不编造」的人话解释闸门结论。
- **演示数据**：`docs/scripts/gen-demo-traces.py` 调用真实接口生成 5 组 trace（2 组放行：0.708 / 0.779；3 组拒答：0.534 / 0.425 / 0.431），结果存于脚本同目录 `demo-traces-result.json`。

### 2.5 性能

- 端到端响应：**1.6 ~ 2.7s**（含向量检索 + DeepSeek 流式首字）
- 检索：40 块规模全量内存余弦 < 10ms；数据量增长可无感切换 pgvector HNSW
- 流式输出：SSE 分帧由框架负责，首字延迟主要取决于 DeepSeek，thinking 关闭后显著降低

## 第 3 章 可复现性论证

### 3.1 确定性的构建链路

| 环节 | 复现方式 | 确定性保证 |
| --- | --- | --- |
| 数据库 | Flyway V1~V4 顺序迁移 | 任何空库 clone 后启动即达到相同 schema |
| 后端 | `mvn spring-boot:run` | Maven 锁定依赖版本（pom） |
| 前端 | `npm install && npm run dev` | package-lock.json 锁定 |
| 密钥 | `backend/.env.example` 模板 | 只需替换两个 Key，其余变量有默认值 |
| 数据 | 上传任意规章制度 PDF | 评估可用公开文档，流程与结果结构一致 |

**完整复现步骤 = 本仓库 [README.md](../README.md) 的「10 分钟极速复现指南」**，每步都有可观察的验收标准（上传返回统计、2~3s 流式首字、3 条可展开来源、无依据问题得到拒答）。

### 3.2 演进链路可追溯

- **Git 历史**：每次提交对应一个功能模块或一次 AI 对话的落地（提交信息格式 `feat/fix/docs: 描述`）
- **Prompt 快照**：`docs/prompt-history/` 三份快照覆盖三个核心迭代，含完整 Prompt 链与修复过程
- **问题修复可验证**：每个关键 Bug（SSE 双重前缀、base-url 404、表名漂移、熔断器）的「修复前行为 → 修复后行为」在快照中均有日志级证据

### 3.3 原创性声明

本项目为参赛者原创，无已有开源项目包装。AI 生成代码的过程、约束手段与演进路径全部公开于本仓库（prompt-history + Git 历史），接受评审核验。
