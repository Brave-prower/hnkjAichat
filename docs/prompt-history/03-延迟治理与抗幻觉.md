# AI 协同演进记录 · 快照 3

## 响应延迟治理与抗幻觉强化

> 本快照对应核心功能迭代：**性能优化（44s → 2s）与防幻觉机制**。
> 展示如何把一段模糊的用户反馈（「回答等待时间长，回答抗幻还得加强」）转化为可量化的工程任务。

---

### 迭代背景

用户实测反馈两条：①从提问到回答输出等待太久（日志显示约 44s）；②问「有啥专业」这类问题时，系统挂了 3 条不相关的来源引用，回答有编造倾向。

### Prompt 1（模糊反馈 → 工程问题拆解）

> 看这份截图：回答等待时间长，回答抗幻（抗幻觉）还得加强。帮我从日志里找到延迟的根因，并把防幻觉机制做实。

### AI 拆解与定位

**延迟根因（三层）：**

1. **Embedding 超时占大头**：Embedding Key 失效时，每次提问都要等 HTTP 重试超时（19~42s）才降级到关键词检索 → 方案：**熔断器**，连续失败立即熔断 10 分钟，期间直接走关键词路，不再尝试网络请求；启动时检测占位 Key（`demo-key` 等）直接禁用 Embedding。
2. **DeepSeek 思维链默认开启**：V4 系列 thinking 模式默认 `enabled`，首字延迟高 → 配置 `thinking: disabled` 开关（回答类任务不需要深度推理）。
3. **检索无闸门**：相似度全低于阈值时仍把不相关文本块塞进提示词 → 加**相关性闸门**：Top-K 全部低于阈值则不调大模型，直接回答「制度中未涉及」。

**抗幻觉强化：**

- 重写系统提示词（`qa-system-prompt.st`）：6 条硬性约束——仅依据提供的制度原文回答、无依据必须明说、页码禁止估算、不确定就说不确定等
- 修正 `document_chunks.metadata->>'title'`：此前存的是文档 ID 而非文档标题，来源卡片显示错误（用临时 SQL 批量修正）

### Prompt 2（实现约束）

> 按上面的拆解实施，但注意：熔断器要做成可自愈的（10 分钟后自动恢复尝试）；thinking 开关走配置文件，默认关闭；相关性闸门的阈值走 `campus.qa.*` 配置。改动不要扩散到无关模块。

### AI 实施要点

```java
// JdbcCosineVectorStore —— Embedding 熔断器（核心片段）
private static final int EMBED_BREAKER_THRESHOLD = 1;   // 失败 1 次即熔断
private volatile long embedBreakerOpenUntil = 0L;       // 熔断恢复时间戳

private boolean embedBroken() {
    return embeddingDisabledAtStartup
        || System.currentTimeMillis() < embedBreakerOpenUntil;
}
// tryEmbed 失败 → embedBreakerOpenUntil = now + 10min
// 下一次提问不再尝试网络请求，直接走关键词兜底；10 分钟后自动恢复
```

```yaml
# application.yml —— DeepSeek 思维链开关
campus:
  deepseek:
    thinking-enabled: false
```

```java
// DeepSeekClient —— 请求体动态携带 thinking 配置
private Thinking thinkingConfig() {
    return new Thinking(props.isThinkingEnabled() ? "enabled" : "disabled");
}
```

### 验证结果

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 端到端响应 | ~44s | 1.6 ~ 2.7s |
| Key 失效时的响应 | 每次等 19~42s 超时 | 熔断后 < 1s 走兜底 |
| 不相关问题 | 硬编 3 条不相关来源 | 明确回答「制度中未涉及」 |

### 经验沉淀

- 「等待时间长」这类模糊反馈，要先用日志把耗时拆到**每一次网络调用**，再逐层治理
- 熔断器 + 自愈恢复是外部依赖（LLM/Embedding API）的标准防护形态，比无限重试或永久禁用都好
- 防幻觉不是一句提示词的事：**闸门（不相关就不答）+ 约束（回答格式）+ 引用（可核对）** 三件套缺一不可
