# 「回答反馈闭环」实施提示词（分步执行版）

> **用法**：按顺序把每条提示词复制给 AI 助手执行。每条执行完先验证、再让 AI 单独 commit 一次——
> 5 条提示词 = 5 个功能提交，正好构成比赛要求的「一次 AI 对话对应一个功能落地」演进记录。

---

## Prompt 1 —— 数据层：反馈字段与迁移

```text
给现有的校园 RAG 问答系统增加「回答反馈」能力的第一步：数据层。

现有表 t_chat_record（建表见 V1__init_schema.sql）字段：
id, session_id, question, answer, sources(JSONB), latency_ms, created_at。
对应实体 backend/src/main/java/com/hnkj/qa/entity/ChatRecord.java。

请完成：
1. 新增 Flyway 迁移 V5__add_feedback.sql：
   - t_chat_record 加列 feedback SMALLINT NOT NULL DEFAULT 0（0=未评价, 1=有用, -1=无用）
   - 加列 feedback_comment TEXT（点「无用」时可选填）
   - 加部分索引 idx_chat_feedback ON t_chat_record (feedback) WHERE feedback <> 0
   - 补 COMMENT
2. ChatRecord 实体同步加字段（Integer feedback, String feedbackComment）
3. 先检查流式问答结束后 t_chat_record 是否写入了 answer——如果流式路径漏落库，
   一并补上（流式 done 前保存完整问答记录），否则前端拿不到 recordId 无法评价。

约束：不改动检索与生成逻辑；迁移脚本只增不删。
验收：后端启动 Flyway 自动执行 V5；对 \d t_chat_record 可见新列。
完成后单独 commit：feat: 反馈数据层（V5 迁移 + 流式落库核查）
```

## Prompt 2 —— 反馈提交接口

```text
第二步：反馈提交接口。

1. 新增 DTO：QaFeedbackRequest { recordId Long @NotNull, feedback Integer（只允许 1 或 -1）,
   comment String（可空，最长 500 字）}
2. 新增接口 POST /api/qa/feedback，逻辑：
   - 校验 recordId 存在，不存在返回业务异常（沿用统一 ApiResponse 错误码）
   - 幂等：重复提交覆盖旧值（update feedback 与 feedback_comment）
   - 更新走 @Modifying 原生 UPDATE，不要先查后存
3. 单元测试：合法提交、非法 feedback 值（如 5）被拒、recordId 不存在返回 404 语义错误码。

约束：接口层只做协议转换，业务在 Service。
验收：curl 三连——正常提交、重复提交、非法值。
完成后单独 commit：feat: 回答反馈提交接口（幂等更新）
```

## Prompt 3 —— 知识库健康度统计接口

```text
第三步：管理端统计接口 GET /api/qa/stats，返回：
1. totalAsks：总问答数
2. usefulCount / uselessCount / usefulRate：有用数、无用数、有用率（百分数保留 1 位）
3. lowQualityTop：低分回答列表（feedback = -1 的记录，按 created_at 倒序取 20 条），
   每条含 id, question, answer 摘要(前120字), feedbackComment, sources(JSONB 原样),
   createdAt
4. unindexedAsks：检索模式为 keyword（非语义）的回答数——用于暴露「Embedding 未配置」问题

实现要求：
- 聚合查询用 @Query 原生 SQL 或 JPQL，不要全量拉内存算
- 新建 StatsResponse DTO，字段含义加注释
验收：造 3 条不同 feedback 的数据后 curl 验证数字正确。
完成后单独 commit：feat: 知识库健康度统计接口
```

## Prompt 4 —— 问答页评分交互

```text
第四步：前端问答页加评分交互（Vue3 + Element Plus，现有页面 views/qa/index.vue，
状态在 stores/chat.js）。

1. AI 回答气泡底部（来源卡片下方）加一行操作：👍 有用 / 👎 无用
   - 已评状态高亮，可改选（再次点击同方向 = 取消，feedback 置 0 不需要，只允许改选）
   - 评价要带 recordId：请在消息对象里保留后端返回的问答记录 ID
     （若流式接口未返回 recordId，让后端在 sources 事件或 done 事件里附带）
2. 点 👎 展开一个折叠面板：三个快捷标签「检索没找到 / 内容答错了 / 看不懂」
   + 可选文本框，提交时作为 comment 一并 POST /api/qa/feedback
3. 提交成功 toast「感谢反馈」，失败显示内联错误并可重试
4. 乐观更新 UI，失败回滚

约束：样式沿用现有设计令牌变量（--app-*），不改全局样式。
验收：评一条有用、一条无用带评论，刷新后记录仍在。
完成后单独 commit：feat: 问答页回答评分交互（👍/👎 + 无用原因）
```

## Prompt 5 —— 知识库健康度看板

```text
第五步：文档管理页（views/document/index.vue）顶部加「知识库健康度」区域。

1. 统计卡四枚：总问答数 / 有用率 / 无用回答数 / 待补知识数（= 无用回答数，显示为待办）
   - 有用率按数值配色：≥80% 绿、50~80% 橙、<50% 红
2. 下方「待补知识清单」：低分回答表格（question、无用原因、命中来源、时间），
   每行一个按钮「去补充文档」→ 跳转上传页
3. 页面进入时加载，提供刷新按钮

约束：数据来自 GET /api/qa/stats；不引入新依赖。
验收：问答页点几个 👎 后，本页数字与清单同步变化。
完成后单独 commit：feat: 文档页知识库健康度看板与待补知识清单
```

---

## 提示词设计的四个要点（答辩时可讲）

1. **目标 + 现状 + 约束 + 验收四段式**：每条 Prompt 都先给 AI 现有代码事实（表结构/文件路径），再提需求，最后给可观察的验收标准——避免 AI 凭空猜测项目结构
2. **一次一步、边界收窄**：5 条 Prompt 各只做一个层（数据→接口→统计→前端交互→看板），每步可独立验证
3. **防过度重构**：明确写「不改动检索与生成逻辑」「不引入新依赖」，把 AI 的发挥空间约束在目标内
4. **提交即演进记录**：每条 Prompt 对应一次 commit，构成「一次 AI 对话 = 一个功能落地」的完整链路
